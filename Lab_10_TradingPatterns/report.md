## 1. Мета роботи

Мета роботи полягає в тому, щоб закріпити навички використання поведінкових патернів у C++ та навчитися додавати нову логіку до вже наявного проєкту. Під час виконання роботи потрібно було зберегти попередню предметну область, не дублювати механізми роботи з базою даних і зробити взаємодію між компонентами зрозумілою.

## 2. Короткий опис початкового проєкту

За основу взято проєкт із лабораторної роботи №8. У ньому реалізовано просту систему обліку трейдерів та їхніх біржових заявок. Для збереження інформації використовується SQLite, бібліотека sqlite_orm та Repository.

Основні сутності:

- **Trader** містить ідентифікатор, ім'я, електронну адресу та рівень трейдера.
- **Order** містить трейдера, біржовий символ, напрямок операції, кількість, ціну та статус заявки.
- **SQLiteTraderRepository** відповідає за додавання, пошук, оновлення та видалення трейдерів.
- **OrderService** забезпечує базові операції із заявками.

У попередній роботі також були реалізовані вибірки, сортування, JOIN, групування та приклади транзакцій. У новій роботі ці основні сутності та зв'язок між трейдером і заявками збережені. До заявки додано рівень терміновості, а також окрему таблицю для історії зміни статусів.

## 3. Індивідуальне завдання, варіант 15

Предметна область мого варіанта - біржові заявки.

Для заявки передбачено такі стани:

- Створена;
- Перевірена;
- Виконана;
- Відхилена.

Основний шлях проходження заявки: Створена, Перевірена, Виконана. Зі станів Створена та Перевірена заявку також можна відхилити. Виконана та Відхилена є кінцевими станами.

Для оцінки пріоритету заявки використовуються три параметри: обсяг заявки, терміновість та час очікування. Для сповіщень передбачено дві події: реєстрація заявки та зміна її стану. Підписниками виступають журнал трейдера та модуль статистики заявок.

## 4. Реалізація патерну State

Патерн State використано для керування статусами біржової заявки. Замість того щоб розміщувати всі перевірки переходів у одному великому наборі умов, кожен стан представлено окремим класом.

Створено інтерфейс `OrderState` та класи `CreatedOrderState`, `VerifiedOrderState`, `ExecutedOrderState` і `RejectedOrderState`. Метод `canMoveTo()` визначає, чи дозволений перехід із поточного стану до нового.

Дозволені переходи:

| Поточний стан | Наступний стан | Результат |
|---|---|---|
| Створена | Перевірена | Дозволено |
| Створена | Відхилена | Дозволено |
| Перевірена | Виконана | Дозволено |
| Перевірена | Відхилена | Дозволено |
| Виконана | будь-який інший | Заборонено |
| Відхилена | будь-який інший | Заборонено |

Для створення потрібного об'єкта стану використовується функція `makeOrderState()`. Контекст бізнес-логіки отримує поточну заявку з Repository, створює об'єкт її стану та перевіряє перехід перед оновленням запису.

Історія переходів зберігається в таблиці `OrderStatusHistory`. У ній записуються ідентифікатор заявки, попередній статус, новий статус і час зміни. Оновлення статусу та додавання запису історії виконуються в одній транзакції SQLite. Перед записом Repository повторно перевіряє попередній статус, щоб не перезаписати зміну, яку міг паралельно виконати інший процес. Якщо операція не завершується успішно, зміни не повинні залишитися частково збереженими.

## 5. Реалізація патерну Strategy

Патерн Strategy використано для розрахунку пріоритету заявки. Усі алгоритми реалізують спільний інтерфейс `OrderPriorityStrategy`, тому їх можна замінювати під час роботи програми без зміни коду контексту `OrderPriorityCalculator`.

Вхідні параметри:

- обсяг заявки `quantity`;
- терміновість `urgency` у діапазоні від 1 до 5;
- час очікування `waitingMinutes`.

Реалізовано три алгоритми:

1. **MaximumNormalizedPriority.** Кожен параметр приводиться до нормованого діапазону, після чого береться найбільше значення. Для обсягу використовується орієнтир 1000 одиниць, для терміновості 5, для очікування 120 хвилин. Результат подається у відсотках.
2. **WeightedSumPriority.** Обчислюється зважена сума початкових параметрів із коефіцієнтами 0,5 для обсягу, 0,3 для терміновості та 0,2 для часу очікування. Цей показник використовується для порівняння заявок у межах одного набору даних.
3. **NormalizedWeightedPriority.** Параметри нормуються, після чого обчислюється зважена сума з тими самими коефіцієнтами. Результат приводиться до шкали від 0 до 100.

Клас `OrderPriorityCalculator` зберігає поточну стратегію в `std::unique_ptr`. Метод `setStrategy()` дає змогу замінити алгоритм під час виконання програми. Вхідні параметри перевіряються, щоб уникнути некоректних значень.

## 6. Реалізація патерну Observer

Патерн Observer використано для сповіщення незалежних компонентів про події, пов'язані із заявками. Видавець `OrderEventPublisher` не знає деталей роботи підписників. Він лише зберігає їхні посилання та передає їм події.

Передбачено два типи подій:

- `Registered` - заявка зареєстрована;
- `StatusChanged` - статус заявки змінено.

Реалізовано двох підписників:

- `TraderJournalObserver` зберігає отримані події в журналі;
- `OrderStatisticsObserver` підраховує кількість зареєстрованих заявок та змін статусу.

Для зберігання підписок застосовано `std::weak_ptr`. Це дає змогу видавцю не керувати життєвим циклом підписників. Підключення виконується методом `subscribe()`, відключення - `unsubscribe()`. Перед сповіщенням видаляються застарілі посилання.

Сповіщення про зміну статусу надсилається після успішного завершення транзакції. Таким чином підписники не отримують повідомлення про зміну, яка не була збережена в базі даних.

## 7. Додатковий патерн Command

Як додатковий патерн із каталогу GoF обрано Command (Команда). Він підходить для цієї предметної області, оскільки дії над заявками можна представити як окремі об'єкти.

Інтерфейс `OrderCommand` визначає метод `execute()`. Клас `ChangeOrderStatusCommand` зберігає ідентифікатор заявки та цільовий статус, а під час виконання передає запит до `OrderWorkflow`. Клас `OrderCommandInvoker` запускає команду.

Такий підхід відокремлює створення запиту від його виконання. У майбутньому на цій основі можна додати чергу команд, повторне виконання або журнал дій без зміни основної логіки роботи із заявками.

## 8. Загальна структура та взаємодія компонентів

```text
Користувач
   |
   v
OrderCommandInvoker -> ChangeOrderStatusCommand
                              |
                              v
                         OrderWorkflow
                         /           \\
                        v             v
                 OrderState       OrderEventPublisher
                 (перевірка)       /              \\
                                  v                v
                         TraderJournal       OrderStatistics
                              Observer           Observer
                                  
OrderWorkflow -> IOrderRepository -> SQLiteOrderRepository -> SQLite / sqlite_orm
                                           |
                                           v
                                   OrderStatusHistory

OrderPriorityCalculator -> OrderPriorityStrategy
                           /          |             \\
                          v           v              v
                     Maximum     Weighted      Normalized
                     Normalized    Sum        Weighted Sum
```

Repository відповідає за роботу з даними, State - за правила переходів, Strategy - за алгоритми оцінки, Observer - за сповіщення, Command - за представлення дії у вигляді окремого об'єкта. Це допомагає не змішувати різні завдання в одному класі.

## 9. Керування ресурсами

У проєкті використовується RAII. Поточна стратегія зберігається через `std::unique_ptr`, оскільки нею володіє один об'єкт-контекст. Підписники створюються через `std::shared_ptr`, а видавець зберігає `std::weak_ptr`, щоб не продовжувати їхнє життя штучно. Ручне використання `new` та `delete` не потрібне.

## 10. Перевірка роботи

Для перевірки доменної логіки створено окремий набір тестів `DomainTests`. Він не потребує підключення до бази даних і перевіряє правила патернів окремо.

Перевірено:

- допустимі та заборонені переходи між чотирма станами;
- роботу трьох алгоритмів оцінки пріоритету;
- відхилення некоректних вхідних параметрів;
- отримання подій двома підписниками;
- відключення одного з підписників;
- виконання команди через invoker.

Після компіляції тестового файлу командою `g++ -std=c++20 -Wall -Wextra -pedantic -Iinclude tests/domain_tests.cpp` отримано результат: **All 18 domain checks passed.**

Повний застосунок використовує `sqlite_orm` та SQLite. У середовищі підготовки звіту бібліотека `sqlite_orm` не була встановлена, тому повну збірку застосунку з ORM тут не запускали. Для неї додано `vcpkg.json` і CMake-конфігурацію. Перед здачею потрібно зібрати повний проєкт у налаштованому середовищі Visual Studio та перевірити роботу транзакцій із локальною SQLite базою.

## 13. Контрольні питання

**1. Що таке патерн проєктування? Які проблеми він допомагає вирішувати?**  
Патерн проєктування - це перевірений підхід до типової проблеми в архітектурі програми. Він допомагає правильно розподілити відповідальність, зменшити зв'язність і спростити подальші зміни.

**2. На які групи поділяються патерни GoF?**  
На породжуючі, структурні та поведінкові.

**3. Для чого потрібні поведінкові патерни?**  
Вони описують взаємодію об'єктів, обмін подіями та розподіл відповідальності під час виконання операцій.

**4. Яку проблему вирішує State?**  
Він дає змогу змінювати поведінку об'єкта залежно від його поточного стану та винести правила кожного стану в окремий клас.

**5. Чим State відрізняється від великого if-else або switch?**  
Умови розподіляються між класами станів. Через це додавання нового стану не вимагає постійно розширювати одну велику умовну конструкцію.

**6. Як контролювати переходи між станами?**  
Кожен клас стану визначає допустимі наступні стани. Перед зміною статусу контекст перевіряє результат цього правила.

**7. Для чого потрібен Strategy?**  
Він інкапсулює кілька алгоритмів однієї задачі та дає змогу взаємозамінювати їх через спільний інтерфейс.

**8. Як забезпечується взаємозамінність стратегій?**  
Усі конкретні алгоритми реалізують один інтерфейс і мають сумісний спосіб виклику.

**9. Які переваги та обмеження має Strategy?**  
Алгоритми можна тестувати та змінювати незалежно. Водночас збільшується кількість класів і потрібно окремо визначити, яку стратегію обрати.

**10. Яку проблему вирішує Observer?**  
Він дає змогу одному об'єкту повідомляти кількох незалежних підписників про подію без прямих залежностей від їхніх конкретних класів.

**11. Як підключати та відключати підписників?**  
Видавець надає методи підписки та скасування підписки. У цій роботі це `subscribe()` та `unsubscribe()`.

**12. Чим синхронне сповіщення відрізняється від асинхронного?**  
За синхронного виклику видавець чекає, поки обробники завершать роботу. За асинхронного подія передається в чергу або інший механізм і обробляється пізніше.

**13. Які принципи ООП підтримують State, Strategy та Observer?**  
Вони підтримують інкапсуляцію, поліморфізм, розділення відповідальності та залежність від абстракцій.

**14. Як патерни впливають на зв'язність і розширюваність?**  
Вони допомагають відокремити компоненти один від одного. Нові стани, алгоритми або підписники додаються без значних змін у вже готовій логіці.

**15. Що враховувати під час вибору патерну?**  
Потрібно розуміти проблему, яку він вирішує, враховувати наявну архітектуру, складність реалізації та реальну користь для майбутнього розвитку програми.
