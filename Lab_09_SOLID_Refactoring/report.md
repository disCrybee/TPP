# Звіт до лабораторної роботи № 9

**Тема:** «Рефакторинг програмного коду. Застосування принципів SOLID під час розробки програм мовою C++»

> Перед поданням заповнити назву закладу, ПІБ, групу та викладача.

## 1. Мета роботи
Набути практичних навичок аналізу та вдосконалення структури програмного коду шляхом застосування технік рефакторингу та принципів SOLID; навчитися проєктувати гнучкі, розширювані й придатні до тестування об’єктно-орієнтовані програмні системи мовою C++.

## 2. Аналіз початкової реалізації системи управління бібліотекою

### 2.1. Призначення та обов’язки класів
Початкова програма демонструє спрощену систему бібліотеки. Клас Book зберігає назву й автора книги, виводить інформацію, імітує збереження та надсилання сповіщення. Клас Library зберігає колекцію книг, додає книги, викликає збереження та сповіщення, а також виводить каталог.

### 2.2. Виявлені недоліки та Code Smells
- **Порушення інкапсуляції:** поля title та author відкриті.
- **Надмірна відповідальність:** Book поєднує предметну сутність, виведення, збереження та сповіщення.
- **Надмірна зв’язність:** Library залежить від конкретних допоміжних компонентів.
- **Обмежена розширюваність:** заміна способу збереження або каналу сповіщень потребувала б змін наявних класів.

### 2.3. Аналіз за SOLID

| Принцип | Стан початкового коду | Обґрунтування |
|---|---|---|
| SRP | Порушено | Book має кілька причин для зміни: дані, виведення, збереження та сповіщення. |
| OCP | Частково порушено | Новий спосіб збереження/сповіщення вимагає змін наявних класів. |
| LSP | Безпосереднього порушення не виявлено | У початковій програмі немає ієрархії успадкування. |
| ISP | Безпосереднього порушення не виявлено | Великі інтерфейси відсутні; доцільно створити окремі вузькі інтерфейси. |
| DIP | Порушено | Високорівнева логіка залежить від конкретних компонентів, а не від абстракцій. |

## 3. Результати рефакторингу системи управління бібліотекою

### 3.1. Запропонована структура
Book інкапсулює назву й автора; поля приватні, доступ на читання надають title() та author(). Збереження і сповіщення винесені в окремі інтерфейси IBookRepository та IBookNotifier. Library отримує їх реалізації через конструктор (Dependency Injection).

- **IBookRepository** — абстракція для збереження книги.
- **InMemoryBookRepository** — реалізація сховища у пам’яті.
- **IBookNotifier** — абстракція механізму сповіщення.
- **ConsoleBookNotifier** — сповіщення через консоль.
- **Library** — керує колекцією книг та координує додавання, збереження і сповіщення.

### 3.2. Схема взаємодії
```text
Клієнт → Library → IBookRepository ← InMemoryBookRepository
                  ↘ IBookNotifier  ← ConsoleBookNotifier

Library також містить колекцію Book.
```

### 3.3. Обґрунтування SOLID
- **SRP:** Book зберігає лише стан книги; каталог, сховище та сповіщувач мають окремі відповідальності.
- **OCP:** нові реалізації сховища або сповіщення додаються через інтерфейси.
- **LSP:** реалізації IBookRepository та IBookNotifier взаємозамінні за умови дотримання контрактів.
- **ISP:** використано два вузькі інтерфейси.
- **DIP:** Library залежить від абстракцій; конкретні об’єкти передаються через конструктор.

### 3.4. Перевірка працездатності
Тестова програма перевіряє додавання двох книг, збереження обох записів та два виклики сповіщувача. Тестовий сповіщувач дає змогу перевірити Library без зовнішньої БД або поштового сервісу.

## 4. Виконання Kata — Gilded Rose

### 4.1. Функціональні вимоги
Обрано завдання №2 — Gilded Rose. Звичайні товари втрачають 1 одиницю якості на день, після завершення терміну — 2; якість не може бути від’ємною. Aged Brie поліпшується, звичайна верхня межа — 50. Sulfuras має незмінну якість 80. Backstage passes поліпшуються на 1, 2 або 3 залежно від наближення події, а після події якість стає 0.

### 4.2. Недоліки початкового підходу
- Довгий метод із розгалуженнями для різних типів товарів.
- Умови за текстовими назвами ускладнюють супровід.
- Додавання нового типу вимагає змін центральної умовної конструкції.
- Окреме тестування правил ускладнене через змішування логіки.

### 4.3. Виконаний рефакторинг
Правила винесені в окремі класи, що реалізують IQualityRule. QualityUpdater обирає правило за назвою, а GildedRose делегує оновлення кожного товару.

- NormalRule — звичайні товари: -1 до завершення терміну, -2 після.
- AgedBrieRule — +1 або +2 після завершення терміну; максимум 50.
- SulfurasRule — якість 80, SellIn не змінюється.
- BackstagePassRule — +1, +2 за 10 або менше днів, +3 за 5 або менше; після події 0.

### 4.4. Індивідуальне розширення: Conjured
Додано тип Conjured Mana Cake: за SellIn > 0 якість зменшується на 2, за SellIn ≤ 0 — на 4; SellIn зменшується на 1, нижня межа якості — 0. Правило реалізовано окремим класом ConjuredRule.

### 4.5. Тестування
Реалізовано перевірки assert у C++17 без зовнішньої тестової бібліотеки. Перевіряються: бібліотека; звичайні товари до/після терміну; Aged Brie та межа 50; Sulfuras; Backstage passes за 10, 5 і 0 днів; Conjured до/після терміну; захист від від’ємної якості. Фактичний результат запуску: компіляція успішна, усі 15 перевірок пройшли, програма вивела «All tests passed.».

### 4.6. Відповідність SOLID
- **SRP:** кожен клас правила відповідає за один алгоритм зміни якості.
- **OCP:** новий тип додається новою реалізацією IQualityRule та реєстрацією правила.
- **LSP:** реалізації IQualityRule взаємозамінні в QualityUpdater.
- **ISP:** IQualityRule містить лише операцію update(Item&).
- **DIP:** GildedRose використовує QualityUpdater, а правила взаємодіють через абстракцію IQualityRule.

## 5. Використання інструментів штучного інтелекту
ChatGPT використовувався як консультаційний інструмент для аналізу методичних вимог, пошуку Code Smells, проєктування розділення відповідальності, підготовки прикладу C++-реалізації та тестових сценаріїв. Остаточний код необхідно перевірити та самостійно пояснити під час захисту.

## 6. Висновки
У роботі проаналізовано початкову систему бібліотеки та усунуто проблеми інкапсуляції, надмірної відповідальності й зв’язності. Збереження та сповіщення відокремлено через абстракції. У Gilded Rose правила оновлення якості розділено на стратегії та додано Conjured із подвійним погіршенням якості. Усі 15 перевірок assert пройшли. Робота демонструє застосування SRP, OCP, LSP, ISP та DIP.
